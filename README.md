# Banxa Payment Links — USDT (TRC20) בכרטיס אשראי

מערכת Web ליצירת קישורי תשלום דרך **Banxa Hosted Checkout v2** (API רשמי בלבד: בלי אוטומציה של דפדפן ובלי עמוד תשלום מזויף).

## בדיקת תאימות: מה Banxa מתירה

בדקתי את [תנאי השימוש של Banxa](https://banxa.com/terms-of-use):

* **Part B, cl. 3(b):** הלקוח מצהיר שכתובת הארנק בבעלותו ובשליטתו הבלעדית.
* **Part A, cl. 4.2(f):** הלקוח משתמש בשירות רק עבור עצמו, ולא עבור צד שלישי.
* **Part B, cl. 4(a):** Banxa רשאית לסרב לרכישה לטובת מוטב אחר, או לרכישה של אדם שאינו מי שיצר את ההזמנה.

**המסקנה:** אסור שלקוח ישלם בכרטיס שלו כשה-USDT נשלח לארנק של מישהו אחר, למשל לארנק העסקי שלך. לכן המערכת מיישמת את המודל המותר בלבד:

> **בעל הכרטיס = מקבל הקריפטו.** הלקוח מוסר לך את כתובת ה-TRC20 שלו. אתה יוצר קישור עם סכום קבוע. הלקוח משלם בכרטיס שעל שמו ומקבל את ה-USDT לארנק שלו.

כל מבנה אחר מחייב אישור מפורש ובכתב מ-Banxa בהסכם ה-Partner.

## מה המערכת עושה

| דרישה | יישום |
|---|---|
| פאנל ניהול | כניסה עם סיסמה (scrypt), Cookie חתום, CSRF, הגבלת ניסיונות כניסה |
| סכום, מטבע ורשת קבועים | USD, USDT, TRON (TRC20). הערכים נשמרים בשרת ונשלחים ל-Banxa רק מהשרת |
| Visa/Mastercard | `paymentMethodId=debit-credit-card` (אמצעי הכרטיס של Banxa) |
| ארנק | ארנק הלקוח. נבדק עם checksum מלא של TRON, ונדחה אם הוא ברשימת "ארנקים חסומים" (הארנקים העסקיים שלך) |
| קישור ייחודי | טוקן אקראי של 256 ביט לכל קישור, עם תוקף בשעות |
| הלקוח עובר ישר ל-Banxa | מסך אישור אחד (Banxa מחייבת להציג גילוי נאות לפני ה-Checkout), ואז הפניית 303 למסך התשלום הרשמי |
| מניעת שינוי בדפדפן | פרמטרים ב-URL או ב-POST נזרקים. השרת שולח רק את הערכים שנשמרו |
| אימות כל השדות | כל שדה ש-Banxa מחזירה (סכום, מטבע fiat, קריפטו, רשת, ארנק, tag, אמצעי תשלום, סוג הזמנה, externalOrderId, externalCustomerId, מזהה הזמנה) מושווה להזמנה השמורה, גם בתגובת היצירה, גם ב-lookup וגם ב-Webhook. הלקוח מועבר ל-Banxa רק אחרי lookup מוצלח ותואם |
| אי-התאמה | עצירה מיידית: הקישור נחסם לצמיתות, קישור ה-Checkout נמחק ולא יוצג שוב, ובפאנל מוצגת הסיבה |
| תוקף קישור Checkout | לפי ה-FAQ של Banxa, הקישור תקף לדקה אחת מרגע יצירת ההזמנה ועד הטעינה הראשונה. המערכת מעבירה לקוח רק בתוך 45 השניות הראשונות. אחרי זה הקישור נמחק והלינק עובר למצב `stalled`: בלי העברה ובלי הזמנה חדשה, עד ש-Banxa מדווחת שההזמנה הקודמת נסגרה |
| מניעת כפילויות | רשומת הניסיון (externalOrderId) נשמרת לפני הפנייה ל-Banxa. אם הבקשה מסתיימת ב-timeout, 5xx או תגובה לא תקינה, השרת לא יוצר הזמנה חדשה עד שהוא מאתר את ההזמנה הקיימת דרך GET /v2/orders |
| בדיקת יעד ההפניה | השרת מפנה רק ל-`*.banxa.com` (או `*.banxa-sandbox.com` ב-Sandbox) |
| מניעת שימוש חוזר | הקישור ננעל אחרי תשלום. נעילה אטומית מונעת יצירה כפולה של הזמנה. ניסיון חוזר מותר רק אם ההזמנה פגה או נדחתה (עד 3 ניסיונות). ביטול של Banxa (cancelled) סוגר את הקישור |
| Webhooks | אימות HMAC-SHA256 לפי התיעוד, השוואה בזמן קבוע. האירוע נשמר לפני שמחזירים 200 ומסומן כמעובד רק אחרי lookup מוצלח. אירוע שנכשל מעובד שוב אוטומטית, ו-Webhook מאוחר לא יכול להחזיר סטטוס אחורה |
| גיבוי ל-Webhooks | השרת בודק כל 2 דקות את כל ההזמנות שעדיין לא הסתיימו |
| פרטי כרטיס | **לא עוברים בשרת שלך בכלל.** הלקוח מזין אותם רק אצל Banxa |
| Production | השרת לא עולה עם `BANXA_ENV=production` בלי `BANXA_PRODUCTION_APPROVED=true` |

### מיפוי סטטוסים

| בפאנל | סטטוס ב-Banxa |
|---|---|
| Pending | `pendingPayment`, `waitingPayment` (או שהלקוח עוד לא פתח את הקישור) |
| Payment Completed | `paymentReceived` |
| Verification Pending | `extraVerification` |
| Processing | `inProgress`, `cryptoTransferred` |
| Completed | `complete` (אחרי 2 אישורי בלוקצ'יין) |
| Failed | `cancelled`, `declined`, `expired` |
| Refunded | `refunded` |

הטבלה מציגה גם את **Transaction ID** של Banxa ואת **Blockchain Tx Hash** (`transactionHash`), עם קישור ל-Tronscan.

פירוט מלא של השינויים האחרונים נמצא ב-[CHANGES.md](CHANGES.md).

## הרשאות ופרטים שחסרים כרגע (נדרשים מ-Banxa)

1. **חשבון Partner ב-Banxa** (Hosted Checkout), כולל אישור KYB לעסק שלך.
2. **פרטי Sandbox:** `BANXA_PARTNER_REF` ו-`BANXA_API_KEY`.
3. **זוג מפתחות HMAC:** `BANXA_HMAC_KEY` ו-`BANXA_HMAC_SECRET`. בלעדיהם המערכת דוחה את כל ה-Webhooks ומסתמכת רק על בדיקה תקופתית.
4. **הפעלה בחשבון:** USDT על TRON, וכרטיס (`debit-credit-card`) ל-USD. אפשר לבדוק את זה בכפתור "בדיקת הגדרות מול Banxa".
5. **רישום כתובת ה-Webhook** בדשבורד של Banxa (הכתובת מוצגת בפאנל).
6. **אישור Go-live ופרטי Production נפרדים.** Banxa דורשת סרטון שמראה את הזרימה, כולל הודעת הגילוי הנאות (ההודעה כבר מופיעה בעמוד הלקוח).

## התקנה

```bash
npm ci
cp .env.example .env
npm run hash-password -- 'סיסמה-חזקה-באורך-12+'   # מדביקים את הפלט ב-ADMIN_PASSWORD_HASH
# ממלאים את .env: SESSION_SECRET, PUBLIC_BASE_URL (https), ופרטי Banxa Sandbox
npm test        # 53 בדיקות מקצה לקצה מול Mock מקומי של Banxa, כולל תרחישי כשל
npm start
```

**Docker:** `docker build -t banxa-links .` ואז `docker run --env-file .env -p 3000:3000 -v $(pwd)/data:/app/data banxa-links`.
צריך שרת HTTPS עם דיסק קבוע לקובץ ה-SQLite, למשל Railway, Render או VPS עם Nginx.

## איך יוצרים קישור חדש

1. נכנסים ל-`/admin`.
2. ממלאים סכום ב-USD, שם הלקוח, האימייל שלו, וכתובת ה-TRC20 **שהלקוח מסר לך**.
3. מסמנים את האישור שהארנק שייך ללקוח.
4. לוחצים **Create Payment Link**.

## איך שולחים ללקוח

במסך שמופיע אחרי יצירת הקישור יש כפתור **Copy Link**, ולידו כפתורים לשליחה ב-**WhatsApp** וב-**Telegram**.
הלקוח פותח את הקישור, מאשר שהארנק שלו ושהכרטיס על שמו, ועובר ישר למסך התשלום של Banxa. שם הוא מזין את פרטי הכרטיס ועובר את אימות הזהות (KYC) ואת אימות 3DS.

## איך מוודאים שהעסקה הושלמה

* הסטטוס בטבלה הופך ל-**Completed**, ומופיע **Blockchain Tx Hash** עם קישור ל-Tronscan.
* בדף הקישור (לוחצים על מזהה הקישור) רואים כל Webhook שהתקבל ואם החתימה שלו תקינה, וגם יומן פעולות.
* אפשר ללחוץ "סנכרון מול Banxa" כדי למשוך את הסטטוס ישירות מה-API.
* אם מופיעה אזהרת **Mismatch**, הנתונים ש-Banxa מחזירה לא תואמים למה שנשמר. לא מוסרים שירות ובודקים מול Banxa.

## מעבר ל-Production

1. מסיימים בדיקה מלאה ב-Sandbox: תשלום, Webhook וסטטוס Completed.
2. מקבלים מ-Banxa אישור Go-live ופרטים חדשים.
3. מגדירים `BANXA_ENV=production`, `BANXA_PRODUCTION_APPROVED=true` ואת הפרטים החדשים.
4. רושמים את ה-Webhook בסביבת Production בדשבורד.
5. מפעילים מחדש.
